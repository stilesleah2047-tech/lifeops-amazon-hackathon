# Deploying LifeOps to Render (+ custom domain)

This guide covers deploying the existing LifeOps monorepo to Render **without
changing any application behaviour** — the MCP server (7 tools, Streamable HTTP,
protocol `2025-11-25`), the deterministic planner, the meeting-aware planner,
the optional Bedrock agent + deterministic fallback, and the SPA/UI are all
unchanged. The only deploy-enabling edits were: (1) the BFF now binds Render's
`$PORT` on `0.0.0.0` and serves the built SPA from `apps/web/dist`, (2) a
`render.yaml` Blueprint, and (3) annotated `.env.example` files.

> **Honesty note:** None of the steps below have been executed against a live
> Render account or a live AWS Bedrock endpoint in this session. They are
> prepared, type-checked instructions. Treat the first deploy as the real test.

---

## 1. Topology

Two services (this matches the code exactly — two independent Express apps that
talk over Streamable HTTP via `MCP_BASE_URL`):

| Service | Render type | Exposure | Owns the DB? | Why |
|---|---|---|---|---|
| `lifeops-mcp` | `pserv` (private) | internal only | **yes** (SQLite) | `/mcp` has no auth in code, so keep it off the public internet. Single SQLite writer lives here. |
| `lifeops-web` | `web` (public) | public HTTPS | no | Serves the Vite SPA build + the BFF (`/api/*`). Reaches the MCP server over Render's private network. |

Why not one combined service: the current code runs **two** `app.listen()`
listeners (BFF and MCP), and a Render service exposes exactly one port.
Combining them would require code changes to the transport/wiring, which is out
of scope. Two services keep the contracts byte-for-byte identical.

---

## 2. One-time prerequisites

- A Render account with a **paid instance type** on at least the MCP service
  (persistent disks are not available on Free — see §6).
- Push this repo to a GitHub/GitLab repo Render can read. (Do **not** commit
  `.env`, real secrets, or any `*.db` file — a `.gitignore` should already cover
  these; verify before the first push.)
- (Optional) An AWS account with a Bedrock model enabled in your region if you
  want the LLM agent path. Leaving it unset runs the deterministic engine.

---

## 3. Deploy via the Blueprint (recommended)

The repo ships `render.yaml` at the root. In Render:

1. **New → Blueprint**, pick this repo. Render reads `render.yaml` and proposes
   both services (`lifeops-mcp`, `lifeops-web`).
2. Review and **Apply**. Render will:
   - create the private `lifeops-mcp` service with a 1 GB disk at `/data`,
   - generate a shared `LIFEOPS_API_KEY` on the MCP service and inject the same
     value into the web service (via `fromService`),
   - wire `MCP_BASE_URL=http://lifeops-mcp:8000` on the web service.
3. Set any `sync: false` secrets in the dashboard (Bedrock — see §5). Leave them
   empty to run deterministic.
4. First build + deploy runs automatically.

### Build & start commands (already in `render.yaml`)

| | MCP (`lifeops-mcp`) | Web (`lifeops-web`) |
|---|---|---|
| Build | `npm ci --include=dev && npm --workspace services/mcp-server run build` | `npm ci --include=dev && npm --workspace apps/web run build` |
| Start | `npm --workspace services/mcp-server run start` | `npm --workspace apps/web run start` |

`--include=dev` is **required**: the MCP build needs `tsc` (a devDep), and the
web `start` script runs `tsx server/index.ts` (tsx is a devDep). Render sets
`NODE_ENV=production`, which would otherwise skip devDeps.

`NODE_VERSION=22` is pinned on both services so `better-sqlite3` uses its
prebuilt binary (no node-gyp source build).

## 4. Environment variables

### MCP service (`lifeops-mcp`)

| Var | Required | Value / note |
|---|---|---|
| `NODE_VERSION` | yes | `22` (prebuilt better-sqlite3) |
| `NODE_ENV` | yes | `production` |
| `HOST` | yes | `0.0.0.0` |
| `PORT` | yes | `8000` (fixed so the BFF can address it internally) |
| `MCP_PATH` | no | `/mcp` (default) |
| `DATABASE_URL` | yes | `file:/data/lifeops.db` (on the mounted disk) |
| `LIFEOPS_API_KEY` | auto | generated by Render; shared with the web service |
| `ALLOWED_ORIGINS` | no | empty is fine (BFF server-to-server calls send no Origin) |
| `DEMO_MODE` | no | `true` for the seeded demo dataset |
| `LOG_LEVEL` | no | `info` |

### Web service (`lifeops-web`)

| Var | Required | Value / note |
|---|---|---|
| `NODE_VERSION` | yes | `22` |
| `NODE_ENV` | yes | `production` |
| `PORT` | auto | injected by Render; the BFF binds it on `0.0.0.0` |
| `MCP_BASE_URL` | yes | `http://lifeops-mcp:8000` (Render private DNS) |
| `MCP_PATH` | no | `/mcp` |
| `LIFEOPS_API_KEY` | auto | pulled from the MCP service via `fromService` |
| `DEMO_USER_ID` | no | `demo-user` |
| `AWS_REGION` | if Bedrock | e.g. `us-east-1` |
| `BEDROCK_MODEL_ID` | if Bedrock | **secret**, `sync:false`; empty = deterministic |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` | if Bedrock | **secrets**, `sync:false` |
| `AGENT_ALLOW_WRITES` | no | keep `false` (writes only proposed, not executed) |
| `AGENT_MAX_ITERATIONS` | no | `5` (bounded agent loop) |
| `ALLOWED_ORIGINS` | prod | CORS allowlist (comma-separated). Set to your custom domain, e.g. `https://lifeops.example.com`. **No wildcard** in prod. Dev defaults to localhost. |
| `LIFEOPS_WRITE_TOKEN` | no | **secret**, `sync:false`. Shared operator token that enables write routes. **Unset = writes disabled (403)** — safe default. NOT per-user auth. |
| `RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_MS` | no | per-instance rate limit (default 120 / 60000ms) |

All AWS values are **secrets** — set them only in the Render dashboard, never in
git. If you can attach an IAM role instead of static keys, leave the key vars
empty.

## 5. Enabling the Bedrock agent (optional)

The BFF runs the deterministic engine unless `BEDROCK_MODEL_ID` is set. To turn
on the LLM agent path:

1. In the Bedrock console, confirm the model is **enabled in your region** and
   copy its model ID (e.g. `anthropic.claude-3-5-sonnet-20241022-v2:0` —
   verify current availability yourself).
2. On `lifeops-web`, set `AWS_REGION`, `BEDROCK_MODEL_ID`, and credentials.
3. Redeploy. `GET /api/health` reports `ai.bedrockEnabled: true` and the
   configured model — but note that flag only means it is **configured**, not
   that a successful AWS call has happened. The first real `/api/ask` is the
   test. On any Bedrock error the BFF transparently falls back to the
   deterministic router and reports `mode: "deterministic-fallback"` with a
   `fallbackReason`.

Meeting-aware questions are **always** answered deterministically regardless of
this setting (the time math must be exact).

## 6. SQLite persistence & backups

The MCP server is the **only** SQLite writer (the BFF never opens the DB — it
only imports the pure, I/O-free `meetingPlanner` function). That single-writer
model is safe as long as there is exactly one MCP instance with a stable disk.

- `render.yaml` mounts a 1 GB disk at `/data` and points `DATABASE_URL` at
  `file:/data/lifeops.db`. The DB layer creates the parent directory at boot.
- **Do not scale the MCP service beyond 1 instance** — multiple writers on one
  SQLite file will corrupt it.
- **Backups:** Render disks are not automatically backed up. For a simple
  backup, open a shell on the MCP service and copy the DB using SQLite's online
  backup (safe while running):
  ```bash
  sqlite3 /data/lifeops.db ".backup '/data/backup-$(date +%F).db'"
  ```
  then download it, or add a scheduled job that uploads it to object storage.
- **Free tier (no disk):** if you must use Free, drop the `disk:` block and the
  data becomes **ephemeral** — the SQLite file is wiped on every deploy and
  restart. Acceptable for a seeded demo (`DEMO_MODE=true` reseeds), not for real
  data.

## 7. Custom domain

Attach a domain (e.g. `lifeops.example.com`) to the **public** `lifeops-web`
service only — the MCP service stays private.

1. In Render → `lifeops-web` → **Settings → Custom Domains → Add Custom Domain**,
   enter the subdomain (e.g. `lifeops.example.com`). Render shows the DNS target,
   which is your service's `*.onrender.com` hostname.
2. At your DNS host, add a **CNAME** record:
   - **Host / Name:** the subdomain label only (e.g. `lifeops`)
   - **Value / Target:** your `lifeops-web` `*.onrender.com` hostname
   - Leave that host with only this one record; don't stack conflicting records.
   - For an apex/root domain (`example.com`), use your DNS provider's
     ALIAS/ANAME/flattened-CNAME feature instead (a plain CNAME is not valid at
     the apex), or follow Render's A-record instructions.
3. Back in Render, click **Verify**. Once DNS resolves, Render issues a free
   **Let's Encrypt** TLS certificate automatically. Propagation can take up to
   24 hours (often much less).

Nothing in the app hardcodes a hostname, so no code change is needed for the
custom domain. (If you later add OAuth/Bedrock callbacks or absolute URLs that
must match the domain, update those env vars then.)

## 8. Post-deploy smoke checks

After the first deploy:

```bash
# Public health (should return ok:true and the honest ai.* capability block)
curl -s https://<your-domain-or-web-onrender-url>/api/health

# Today snapshot (deterministic; exercises the MCP private link)
curl -s "https://<...>/api/today?userId=demo-user"

# Natural-language ask (deterministic unless Bedrock configured)
curl -s -X POST https://<...>/api/ask \
  -H 'content-type: application/json' \
  -d '{"userId":"demo-user","prompt":"plan my afternoon"}'
```

Expected: `/api/health` → `ok:true`; `/api/today` returns tasks/schedule/
insights/summary with an `activity` feed of real tool calls; `/api/ask` returns
a `mode` of `deterministic` (or `bedrock` / `deterministic-fallback` if Bedrock
is on). If `/api/today` errors with a connection failure, the web service can't
reach the MCP service — recheck that both are in the **same region** and that
`MCP_BASE_URL` matches the private service name and port.

## 9. Security posture (Phase 3.1 hardening — read carefully)

**There is no end-user identity system.** `userId` is a request parameter that
defaults to the demo user. The hardening below does **not** add per-user
authentication or authorization — doing so is a larger design decision (see
below). What the public BFF now enforces:

- **CORS is a configurable allowlist**, not wildcard. Set `ALLOWED_ORIGINS` to
  your custom domain in production. Same-origin requests (the SPA this service
  serves) and non-browser clients send no `Origin` and are allowed — CORS is a
  browser policy and is **not** treated as authentication.
- **Write routes are gated by a shared operator token.** `complete_task` (via
  `POST /api/tasks/:id/complete`) and `create_reminder` (via a `/api/ask`
  “remind me…” prompt) require `Authorization: Bearer <LIFEOPS_WRITE_TOKEN>`.
  - **Token unset (default) → writes return `403`** and can never be triggered
    anonymously. This is the recommended public-beta posture: a **read-only
    demo**.
  - Token set → the caller must present it. This authenticates *whoever holds
    the token*, **not an end user**. If you expose it to the browser via
    `VITE_LIFEOPS_WRITE_TOKEN` so the demo “Mark done” button works, be aware
    the token is then visible to anyone using the site — it only deters casual
    and cross-site abuse.
- **Agent writes stay off** unless `AGENT_ALLOW_WRITES=true` **and** the caller
  is write-authorized. Default remains `false`.
- **Rate limiting**: a per-instance fixed-window limiter on `/api/*`
  (`RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_MS`). Per-instance only — use a shared
  store if you scale beyond one web instance.
- **Validation & limits**: request bodies are validated (prompt required and
  ≤500 chars; `taskId` shape-checked) and capped at 256 KB.
- **Secret-safe errors**: in production the client receives a generic
  `Internal server error`; the full error is logged server-side only.
- **MCP stays private**: `/mcp` is only reachable from the BFF over Render's
  private network, and additionally shares `LIFEOPS_API_KEY`.

### Known residual risk (requires a design decision — NOT implemented here)

- **No per-user authorization / IDOR on reads.** Because `userId` comes from
  the request, a caller can read any user's data by changing it. In the
  single-demo-user deployment this is moot, but **before onboarding real,
  multiple users you MUST**: (a) add real authentication (session login or
  OAuth/OIDC), (b) derive `userId` from the authenticated session — never from
  the request body/query, and (c) scope every tool call to that identity.
- Options for that step, to review before building: a lightweight email+session
  (cookie) layer in the BFF; a hosted IdP (Cognito/Auth0/Clerk) in front of
  `/api/*`; or Render-level access control for a private beta. This was left
  out deliberately — it changes the data model and UX and should be reviewed,
  not introduced unreviewed.

### Local development

`ALLOWED_ORIGINS` defaults to `http://localhost:5173,http://localhost:3000`
when unset in dev, so the Vite workflow keeps working. To exercise write
actions locally, set `LIFEOPS_WRITE_TOKEN` in `apps/web/.env` and
`VITE_LIFEOPS_WRITE_TOKEN` to the same value; leave both unset to test the
read-only (403) default.
